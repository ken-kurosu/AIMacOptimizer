## 1. ミッション / ポジショニング

### ミッション

**「Macの容量とスピードの話から、"盛った数字"をなくす。」**

Mac最適化ジャンルの検索結果は、次の2種類でほぼ埋まっている。

1. **アフィリエイト目的の一般論記事** — 実機で試しておらず、スクショはメーカー提供素材。「最大○GB解放！」と製品側の宣伝数値をそのまま転載
2. **メーカー公式ブログ** — 自社製品が常に結論。「解放できる*はず*の容量」という予測値で期待を煽る

このメディアは第3の立場を取る。**すべての主張に、実機で計測した前後の数字を付ける。** 「キャッシュを消すと速くなる」ではなく「M2 MacBook Air / macOS 15で、Chromeキャッシュ4.2GBを削除→再起動後の実測で3.8GB空いた（0.4GBは即再生成された）」と書く。

### ポジショニング: 「実測で正直」のコンテンツ拡張

アプリの差別化核「実測で正直」（最適化前後を実測し、実際に空いた分だけ表示する）を、そのまま編集方針にする。

| アプリの価値 | メディアでの拡張 |
|---|---|
| 削除前後の実サイズ差だけを表示 | 全記事にBefore/After実測値を掲載。「効果があるはず」の一般論を書かない |
| 安全な対象だけを自動検出 | 「消していい/触るな」を必ず明示。安全側に倒した手順だけ推奨 |
| リスク操作は1件ずつ承認 | 読者に「まずリスクゼロの手順から」の順序で提示（1本目記事の型を踏襲） |

### 競争優位（堀）

1. **一次データの堀**: 実機計測（機種・macOSバージョン・前後の数値・再現手順）は、書き手が実際にMacとアプリを持っていないと書けない。生成AIで量産される一般論記事に対する最強の防壁であり、GoogleのE-E-A-T（特にExperience）にも直結する
2. **開発者の堀**: アプリ開発で得た知見（purgeable領域の挙動、`~/Library`配下の安全性分類、macOSバージョン差分）は、開発者でなければ書けない深さになる
3. **利益相反の少なさの堀**: 無料で完結する手順（再起動・ゴミ箱・手動削除）を隠さず先に書く。自社アプリは「判断の自動化」という最後の一歩でだけ登場する。この誠実さが指名検索とリピートを生む

### 書かないこと（編集タブー）

- 実測していない効果の断言（「○GB空きます！」）
- 恐怖煽り（「今すぐ消さないとMacが壊れる」）
- 競合の誹謗（CleanMyMacとの比較は機能・価格・表示方式の事実比較に限定する）
- SIP無効化・システム領域の手動削除など、リスクの高い手順の推奨

キーワード3層を、読者の課題単位で5ピラーに再編する。①②③の層とピラーは1対1ではなく、**ピラーA=①、B/C=②、D=③、E=横断（堀）**という対応。

- **役割**: 最大の入口。診断→原因切り分け→各論（B/C/D）へ内部リンクで流す配水塔

## 5. コンテンツ種別と役割

| 種別 | 目的 | 主なピラー | CTAの強さ | 本数比率目安 |
|---|---|---|---|---|
| **ハウツー（手順記事）** | SEO集客の主力。検索意図に即答し、最後に「判断の自動化」としてアプリを提示 | A/B/C | 中（記事末＋文中1箇所） | 50% |
| **トラブル解決** | 「減らない」「固まる」等の緊急検索を拾う。信頼獲得優先でCTA弱め | A/B | 弱（記事末のみ） | 15% |
| **比較・代替** | CV記事。事実ベース比較でDLへ直行させる | D | 強（比較表内＋文中＋記事末） | 15% |
| **実測レビュー/レポート** | 一次データの供給源。被リンク・SNS共有・E-E-A-T。他記事から「根拠」として参照される | E | 弱（データの信頼を汚さない） | 15% |
| **用語解説** | `purgeable` `スワップ` `SSD 寿命`等。ロングテール＋内部リンクのハブ。滞在の受け皿 | 横断 | 弱 | 5% |

**役割分担の原則**: SEO集客記事（ハウツー/トラブル）は「無料で完結する解決」を出し惜しみせず、CVは比較記事とアプリ紹介ページに集中させる。集客記事の役割はDLを迫ることではなく、**比較記事・LPへの内部リンク送客と信頼形成**。

## 7. メディア → LP → アプリDL のファネル設計

### ファネル全体

```
検索(①②③) → 記事 → [CTA] → LP(aimacoptimizer.github.io) → .dmg DL → 起動 → 無料利用 → Pro
                ↘ 内部リンク → 比較記事/blog/app/ → LP（間接CV）
```

### 記事内CTAの型（3種）

1. **文中ブリッジ型**（ハウツー記事の「手動の限界」直後）: 1本目記事の型を標準化。「難しいのは作業ではなく判断。そこを自動化し、実際に空いた分だけを見せるのが──」の流れでテキストリンク。押し付けない
2. **実測ボックス型**（記事中盤〜後半）: Before/After実測値＋スクショを枠で見せ、「自分のMacで測る（無料）」ボタン。**数字が広告**という本メディア独自の型
3. **記事末カード型**（全記事共通）: アプリ名/一言（盛らない・実測・無料スキャン無制限）/対応OS/公証済み/DLボタンの定型カード。比較記事のみ「買い切り¥4,980」の価格訴求を追加

### UTM設計（既存記事の規約を継承・拡張）

```
utm_source = media（自メディア） / note / zenn（外部配信）
utm_medium = article
utm_campaign = {記事slug}（例: system-data, cleanmymac-alternative）
utm_content = inline | labs-box | footer-card（CTA位置の効き比較用）
```

### KPI（計測はGA4 + Search Console。LP側にもGA4を入れ、クロスドメインになる場合は設定必須）

| ファネル段階 | KPI | 90日時点の目安 |
|---|---|---|
| 集客 | 検索表示回数 / クリック / 掲載順位（GSC） | 指標の器を作る段階。主力5記事が50位以内に入れば順調 |
| 記事 | セッション、記事完読率（90%スクロール） | 完読率 40%〜 |
| 送客 | **記事→LPクリック率（最重要KPI）** | ハウツー記事 2〜4% / 比較記事 8〜15% |
| CV | LP→DL率、DL数/月 | LP→DL 20%〜（メディア経由は検索意図が濃いため広告より高いはず） |
| 収益 | DL→Pro転換（アプリ側計測） | メディアの責務外だが、utm_campaign別の転換差は記事企画に還流する |

**運用ルール**: 月次で `utm_campaign`別のLPクリック→DLを見て、送客効率の高い記事型（おそらく比較記事と実測ボックス型CTA）に翌月の制作を寄せる。

## 8. 公開・技術スタックの推奨

### 比較

| 案 | 初期コスト | ランニング | SEO | 運用工数 | 評価 |
|---|---|---|---|---|---|
| **A. Astro + GitHub Pages（現インフラ延長）** | ¥0 | ¥0（独自ドメイン取得時 約¥1,500/年） | ◎ 静的HTML・Core Web Vitals満点圏。LPと同ドメイン統合で資産合算可 | 中（初期構築1〜2日、以後はMarkdown追加のみ） | **◎ 推奨** |
| B. WordPress + レンタルサーバ | 数千円 | 約¥12,000/年 | ○ 実績十分だが速度・保守で劣後 | 高（更新・セキュリティ・プラグイン保守） | △ ソロ運営の保守負担が無駄 |
| C. note / Zenn のみ | ¥0 | ¥0 | △ ドメインは強いが、資産が他社プラットフォームに残る。カスタムCTA・計測・構造化データ・カテゴリ設計の自由がない | 低 | △ 主戦場にはしない |
| D. Notion + 公開サービス系 | ¥0〜 | 〜¥1,000/月 | △ URL構造・速度・構造化データの制御が弱い | 低 | ✕ |

### 推奨: 案A「Astro + GitHub Pages」

理由:
1. **現LPが静的HTML+GitHub Pagesであり、同一スタック**。ビルド→デプロイはGitHub Actionsで自動化でき、追加インフラも費用もゼロ
2. AstroはMarkdownベースのContent Collections・sitemap/RSS/OGP自動生成・構造化データ挿入が標準的にでき、**記事執筆=mdファイルをコミットするだけ**の運用になる（Claude Codeでの記事量産とも相性が良い）
3. 静的生成のためCore Web Vitalsで満点圏を狙え、技術面のSEO減点がない

補足方針:
- **ドメイン**: まず `aimacoptimizer.github.io/blog/` で開始（github.ioはPublic Suffix運用のためサブドメイン間でスパム評価が波及しない）。記事が10本を超え手応えが出た段階で独自ドメイン（`aimacoptimizer.com` 推奨・約¥1,500/年）を取得し、**LPとメディアを同一ドメインに統合**して301リダイレクト。メディア専用ドメイン分離は資産分散になるため行わない
- **note/Zenn の位置づけ**: 「併用するが主戦場にしない」。noteはcanonical指定不可のため**自サイト記事の全文転載は禁止**。noteには要約＋実測ハイライト版を書き自サイトへ誘導、Zennにはンジニア向け技術記事（ピラーC/E系）を書いて開発者認知と被リンクを取る。既存1本目（note/Zenn想定で執筆済み）はそのまま外部配信に使い、自サイト版は計測データと構成を差し替えた別稿として公開する
- **コメント/検索等の動的機能**: 初期は持たない。必要になったら静的検索（Pagefind）を足す

### ソロ運営の効率化メモ
